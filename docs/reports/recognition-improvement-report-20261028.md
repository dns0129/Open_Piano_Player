# 识谱模型与规则检查及提升报告（2026-10-28）

本报告只做检查，不改动识谱行为。依据为当前 `main` 的代码与已有评测记录；未发起新的模型调用。

## 一、现状

| 项 | 当前配置 |
|---|---|
| 主模型 | `gpt-6.1-sol` / `high`，经 Pi 调用，请求前后核对模型与档位（`lib/recognition-policy.mjs`） |
| 备选 | `deepseek-flash` / `high`（`lib/deepseek-vision.mjs`） |
| 提示词 | `piano-source-assessment-v6-20261026`：双手系统分组、升降号专项、原谱问题评估三块规则（`lib/recognition-prompts.mjs`、`lib/source-assessment.mjs`） |
| 调用策略 | 每行 1 次调用，已取消独立复读；不自动重试，超时 10 分钟，输出上限 6 万 tokens |
| 本地规则 | 每手每小节拍数缺口、小节超时值、同声部重叠、小节数、延音接续、原图音头坐标（`lib/score-region.mjs`） |

已有实测数据：

| 场景 | 结果 | 来源 |
|---|---|---|
| 清晰排版肖邦前奏曲，按思考档位 | low 88.3% → high 98.3% → max 99.3%（严格 F1） | `GPT61客户端三档识谱-20261018/` |
| 密集 PDF，3 份共 16 行 | 返回音符精确率 99.8%，召回 64.3%；16 行中 5 行整行失败 | [dense-pdf-benchmark-20261021.md](dense-pdf-benchmark-20261021.md) |
| 手机整页照片 | 24 张中 6 张结构完整；同图裁成单系统后 16/16 一致 | [phone-score-accuracy-20261021.md](phone-score-accuracy-20261021.md) |
| 《幻听》，7 个升号 | DeepSeek 原始结果 6.2% 与参考一致；GPT 两次读取 24/28 行一致 | `output/幻听-*-六页验证/` |

以上样本量小、非随机抽样，不能外推为通用准确率。

核心判断：主要损失不在“读错音”，而在两处：

1. 整行拒识或失败，拉低召回；
2. 升降号和线间位置读错。这类错误能通过全部结构检查，本地规则抓不到。

## 二、P0：投入小、收益明确

### 1. 速度未知会让整行作废

- 密集 PDF 评测中有一行 102 个音符全部读对，只因模型返回 `bpm=0`，整行判失败。
- [recognition-strategy.md](../recognition-strategy.md) 写明“没有数字标速时用可编辑的练习默认速度”，但该兜底只存在于 `scripts/reread-five-high.mjs`。App 正式流程中，`compactRegionSchema` 要求 `bpm≥20`，`validateScore` 也要求速度在 20–300。
- 建议：允许 `bpm: null`。缺速度时沿用上一行；首行用 90 并标为“未印速度”，不再因此拒收整行。

### 2. 校验失败时，模型拿不到有用的错误信息

- `lib/recognition-wire.mjs` 的 `decodeCompactRegion` 不论哪里出错，都只抛出同一句“紧凑谱行格式无效”。
- Pi Agent 允许最多 3 轮，但模型不知道错在哪，补救成功率很低。
- 建议：
  - 错误信息具体到“第几个音符、哪个字段、为什么”。
  - 把本地拍数缺口、超时值、小节数检查放进提交工具内执行，失败即回传模型，最多补救 1 轮。
  - 补救沿用现有原则：只按原图修正，不许为凑拍补写。

## 三、P1：提升准确率的关键

### 3. 输出协议只回传 MIDI，升降号规则无法落到代码（最重要）

- 提示词要求先读谱号和线间位置，得出音名字母、八度，再加升降号；但输出格式只有 `[MIDI, 起拍, 时值, 声部, …]`，书写信息全部丢失。之后 `lib/pitch-spelling.mjs` 只能按调号反推拼写，“B♯ 不能写成 C”这类规则无法保证。
- 对应实测错误：
  - 拉赫玛尼诺夫前奏曲 B♯4（72）被读成 70；
  - DeepSeek 在 7 升号调中多次整体偏差 5 或 10 个半音，属线间位置读错。
- 建议：每个音额外输出“谱表 + 线间位置（相对谱号的级数）+ 是否有显式升降号”，每个谱表输出谱号及谱号变化。MIDI 由本地按“调号 + 逐小节临时记号”计算；模型给出的 MIDI 与计算结果不一致即标为疑点。
- 这样升降号规则从“请模型遵守”变为“代码保证”。`skills/piano-score-to-musicxml/SKILL.md` 已按“字母 / 八度 / 升降值”记录，App 应对齐。

### 4. 密集行拒识缺少自动降级

- 肖邦 Op.10 No.4 召回仅 43.6%，主要因模型主动返回 `NEEDS_SOURCE`。
- 《幻听》末行在第 3 次、使用 2 倍尺寸原图才读成功。
- 放大局部图（`detailImages`）目前只在数字 JSON 降级流程和脚本中使用，主识别流程未接入。
- 建议：某行拒识后，自动走只限该行的降级链：
  1. 2 倍原图加放大局部；
  2. 仍失败则按小节对半切开，保留重叠区域；
  3. 最后用 `max` 档。
- 只有失败的行才额外付费。

### 5. 取消复读后，缺少自动发现错音的手段

- 取消独立复读后每行调用从 2 次降到 1 次，但“两次读法不一致”是唯一能自动发现错音的信号。
- 结构检查对错音无效：DeepSeek 首行 13 个音只对 2 个，`checks.passed` 仍为 true。
- 建议：只对高风险行复读，复用 `lib/reading-consensus.mjs`。触发条件可为：调号 ≥4 个升降、临时记号多、音头密集、有换谱号、模型给出警告，或首行。
- 也可只放大复读带临时记号的小节，成本远低于整行复读。

### 6. 单图识别与整谱逐行识别是两套规则

- 单图使用 `lib/ai.mjs` 的 `instructions` 与 `scoreSchema`：没有休止、声部、延音字段，最短时值 0.0625，无法做拍数缺口检查。
- `regionScoreSchema` 与 `acceptScoreRegion` 在生产代码中已无调用，仅测试使用。
- 建议：单图也改用逐行紧凑协议，删除旧格式定义，避免规则继续分叉。

## 四、P2：工程与治理

### 7. 规则文档版本不一致

| 位置 | 记录的版本 |
|---|---|
| 代码 `RECOGNITION_PROMPT_VERSION` | `piano-source-assessment-v6-20261026` |
| [recognition-strategy.md](../recognition-strategy.md) | `expressive-timing-v3-20261019` |
| README | `accidentals-v2-20261018`，且仍描述每行独立复读 |
| Skill | `accidentals-v2-20261018` |

建议：加一个测试，断言文档中的版本号等于 `RECOGNITION_PROMPT_VERSION`。

### 8. 提示词换版本时没有准确率把关

各轮评测口径不同。已有带参考答案的样本：前奏曲 602 音、密集 PDF 1292 音、《幻听》1068 音、BWV846 549 音、手机照片 36 音。建议固定为回归集，统一评分器，每次改提示词都运行，分别报告精确率、召回、升降号准确率和整行拒识率。

### 9. DeepSeek 准确率低且易漏提交

只有一次机会，`tool_choice` 为 `auto`，模型可能不调用提交工具。建议标为“实验 / 第二意见”，不作为平等选项；如接口支持，改为强制调用工具。

### 10. 本机测试环境

本机为 Node 21.3，项目要求 ≥22.19（`.nvmrc` 为 24）。识谱相关 17 项测试中有 8 项因无法加载 `.ts` 文件（`ERR_UNKNOWN_FILE_EXTENSION`）失败，属于环境问题。建议安装 Node 24，否则无法在本机验证上述改动。

## 五、建议顺序与预期

1. P0 两项：救回“读对却被判失败”的行；按密集 PDF 样本，16 行中至少可救回 1 行。
2. 第 3 项结构化音高：提升升降号准确率的根本办法，需要改输出协议、增加本地临时记号计算，并使旧缓存失效。
3. 第 4、5 项：把付费重试和复读集中到失败行与高风险行，目标是把密集谱召回从 64% 推向 90% 以上（需回归集验证）。
4. 第 7、8 项：回归集建立后，每项改动的效果才能量化。
